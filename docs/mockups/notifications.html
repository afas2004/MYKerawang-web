Notifications — audit & proposal

MYKerawang · drafted 13 Nov 2026 · design only, nothing built yet

Words used here

In-app notification — a row in the bell list inside the app. Only seen when you open the app.
Push notification — a message the phone shows on its lock screen even when the app is closed.
PWA (progressive web app) — our website "added to home screen", so it opens like a normal app.
Service worker — a small script the browser keeps in the background for a website. It is the only thing that can receive a push while the app is closed.
Web Push — the browser standard for push. Chrome, Edge, Firefox and Safari all support it. On iPhone it works only when the app is installed to the home screen (iOS 16.4 or newer).

How the bell and the count work

  • The red count is live. unread_notifications.dart listens to the database in real time (Supabase Realtime) and recounts on every change. No refresh needed.
  • The list is live too (it uses a stream).
  • Pop-ups don't work on the web. main.dart listens for new rows and calls NotificationService.showNotification, but that function does nothing on web (it is built on flutter_local_notifications, which has no web support). Since the app is web-only, nobody sees a pop-up — the package in pubspec.yaml is unused weight.
  • Text is stored in English only. Titles are written into the row when it's created, so a Malay or Japanese user reads English notifications.
  • No push of any kind exists. Nothing reaches you when the app is closed.

Step 2 — Proposal

Recommendation: Option 1. Everything (notifications, users, preferences) already lives in Supabase, so the sender sits next to the data, and no extra Firebase SDK is loaded on students' phones.

B. How the server sends

Something happens (comment, form answer…)→row added to notifications→Database Webhook→Edge Function send-push→checks your settings, quiet hours, grouping→phone
  • A Database Webhook is a Supabase setting that calls a URL whenever a row is inserted. An Edge Function is a small server program Supabase runs for us.
  • The bell keeps working exactly as now; push is an extra copy of the same row. If push fails, nothing is lost.
  • A new table push_subscriptions holds each device's push address. Dead addresses (uninstalled app) are deleted automatically when the push service says "gone".
  • Cost on the free plan: Edge Functions allow 500,000 calls a month. 1,000 active users × 5 notifications a day ≈ 150,000 a month — well inside. Web Push delivery itself is free.
  • Text is chosen in the reader's language: we save the language the user picked in Settings to their profile, and the function writes the push in en / ms / ja.

C. The service worker — without breaking updates

Every deploy copies sw_reset.js over flutter_service_worker.js. That old worker deletes itself so phones always load the newest app. A browser allows one worker per folder ("scope"); if the push worker shared the root folder, the reset worker would replace it and push would silently stop after the next deploy.

Put the push worker in its own folder: web/push/sw.js, registered with scope /push/. It only handles two things — "a push arrived" (show it) and "a notification was tapped" (open the right page). It caches nothing, so it can never serve old app code, and sw_reset.js and deploy_web.bat stay as they are.

Risk to check on a real iPhone early in the build: Apple's push with a non-root worker scope. Fallback if it misbehaves: one root worker that does reset-cleanup and push (a bigger change to the update mechanism).

D. Not spamming people

  • Grouping: likes, form answers and event joins are merged in the bell ("Aina and 4 others…") and on the phone (the newer push replaces the older one for the same post/form).
  • Pace: at most one push per post/form per 15 minutes; at most 8 pushes a day per person (event reminders and safety notices are exempt).
  • Quiet hours: default 11 pm – 7 am Malaysia time. Pushes are held; the bell still fills. Event reminders still come if the event is inside the quiet hours.
  • New-event broadcast: stop sending it to every user. Bell-only and off by default (opt-in in Settings).
  • Likes are never pushed — bell only.

E. Event reminders

A scheduled job inside the database (pg_cron, free on Supabase) runs every 5 minutes and creates a reminder for people who joined an event starting in about 1 hour, plus an optional evening-before reminder (8 pm). Each reminder is sent once only.

F. Asking for permission

  • Never on first load — browsers punish sites that ask too early, and a "Block" is permanent until the user digs into settings.
  • Ask right after a moment where push clearly helps: after joining an event ("Remind me 1 hour before?"), after publishing a form, or from the bell's banner.
  • Our own friendly sheet first; the browser's prompt only appears if they tap "Turn on".
  • iPhone in Safari (not installed): instead of asking, show "Add MYKerawang to your Home Screen to get alerts" with the 3 steps.

Decisions for you

1. Push route: Plain Web Push (recommended), Firebase, or no push for now?
2. Which missing types to add: comments on my post, replies, likes (bell only), form answers, event starts soon, event changed, someone joined my event, What's new?
3. The "new event" broadcast to every user: make it opt-in, bell only (recommended), keep as is, or remove?
4. Reminder timing: 1 hour before only, or also the evening before?
5. Quiet hours default: 11 pm – 7 am, or off by default?
6. Build all four phases in one go, or Phase 1–2 first and push after?
